Crew mode — your day, once it is on

The other chart was how to switch it on. This one is what your evenings look like after. Same merge button, same rules, more hands. Nothing here is new to learn — it is the loop you already run, with the number of things in flight raised from one to a few.

It is called crew mode. The switch is the first line of docs/CREW-MODE.md: MODE: off → MODE: on. Every session reads it at start (CLAUDE.md, step 3½). You can also just say "crew mode on for this one" and it applies to that session only, without touching the file. A session that is unsure is off.

The unit is a RUN — one sitting, a few tickets, a few PRs

In normal mode the unit is a ticket. In crew mode the unit is a run: you name a handful of issues, they get worked at the same time, and they come back to you together. A run is over when you have merged or rejected everything in it. You never have two runs open at once — that is the thing that keeps this legible.

Step 1 · you open the run

1
you · 2 min
Name the issues and the size.

Look at the open list, pick the ones you want, say so. The number is the budget — say it out loud or you will get everything.

crew mode on — run #128, #129 and #150

Or if you would rather not pick: crew mode on — take the top three by tier

2 minutesreversible — say stop at any point

Step 2 · they claim, in the open

2
the crew
Each agent labels its issue taken: before it starts.

This is the lock. Two agents cannot take the same issue, and you can see who has what by walking the town — the label shows on the stall. Nothing else about the issue changes.

nothing lands on you

Step 3 · they work, each in its own folder

3
the crew
One branch and one worktree per agent.

Branch names carry the issue number — claude/129-.... Nobody edits anybody's files, because nobody shares a folder. Each writes its failing test first, then the fix, then runs all four suites until green.

nothing lands on you

Step 4 · you answer, if asked

4
you · 0–5 min
Only taste, story, or how much.

Never something a machine could have worked out. Usually zero or one question per issue, and the rest of the run keeps moving while you think — that is the whole point of running them in parallel.

0–5 minuteseverything on that one ticket waits on you

Step 5 · CI, then the PRs arrive together

5
machine
Each PR is green before you ever see it.

One PR per issue. Red never reaches your merge button. If one goes red it goes back to its own agent and does not hold up the others.

Step 6 · you read and merge — the only step that matters

6
you · ~10 min each
Merge the ones you like. Say no to the ones you don't.

Rejecting costs nothing: the branch and the folder are deleted, the taken: label clears, and the issue goes back on the pile as if it had never been picked up. Use the reading rule — spend your attention on the commits that touch engine/ or content, and take docs commits on trust.

~10 min per PRthe merge is the one irreversible step, and it is still only yours

Step 7 · the run closes itself

7
the crew
Labels clear, branches and folders are deleted, issues are closed in plain words, NEXT-SESSION is rewritten.

You do nothing. The next run starts from a clean street.

What actually changes for you — the honest list

What you will noticeWhy it happensWhat to do about it
Three PRs instead of oneThat is the whole featureRead them in whatever order you like. They do not depend on each other
Issues wearing a taken: labelThe claim is public so two agents cannot collideNothing. It clears itself on merge. A label older than a session is stale and gets taken
Branch names with numbers in themOne branch per issue instead of one long-lived branchNothing. They delete themselves
Two PRs touching the same fileTwo agents landed near each otherMerge the one you prefer. The second rebases and re-runs the suites — the tests decide, not you
Your evening is fullerThree PRs is roughly thirty minutes, not tenThis is the real cost. If it is too much, run two next time instead of three

When you want it to stop

✋
you · 5 sec
Say stop. That is the whole procedure.

stop the run — work in flight is abandoned, labels clear, nothing is merged. crew mode off — back to one thing at a time, permanently, until you say otherwise.

Neither loses anything you had already merged, and neither needs a cleanup step from you.

The four things that never change, on or off. You merge, and nothing else merges. CI is green before you see anything. Every commit stages explicit paths, never git add -A. The public game only ever changes for the public game's sake, and the town never leaks into it. Crew mode dials how many hands are working. It does not touch anything that decides what is safe.

How to tell whether it was worth it

After one run, one question — and it is not "did more get done," because more will always get done:

Ask yourselfIf yesIf no
Did I read all three PRs as carefully as I read one?Keep it on. Try four next timeGo to two, or go back to one. An unread merge is worse than a slow week
Did I have to answer more questions than usual?The tickets were underspecified, not the mode — Remedios sharpens them before the next runNothing to fix
Did two of them collide on the same file?Run tickets from different areas together, not three that touch the same oneNothing to fix

The ceiling on this was never the machines. It is how many pull requests you want to read in one evening, and only you can find that number. Three is where I would start, and it is a number you can change by saying a different one.
