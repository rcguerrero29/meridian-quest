How the Crew Ships

Two pictures. The first is what a git worktree actually is and why one per builder is the difference between several agents working and several agents corrupting each other. The second is the whole path a piece of work takes, from something noticed in play to a merge.

1 · What a worktree is

A git repository is two things that people usually see as one: a store of every commit, branch and object — the .git folder — and a working tree, the ordinary files on disk that you actually edit. Normally there is one of each, so "the repo" and "the files" feel like the same thing.

git worktree separates them. One store, several working trees, each checked out on its own branch, each with its own staging area. That last part is the whole point: staging is where git add collects files, and a separate staging area is why one agent's git add physically cannot reach another agent's files.

# make one — a new directory, a new branch, off main
git worktree add ../wt-131 -b claude/131-sill-skulls origin/main
# the agent works entirely inside ../wt-131 and never leaves it
# after the PR merges, take it away
git worktree remove ../wt-131 && git branch -d claude/131-sill-skulls

Two properties do the work. Git refuses to check out the same branch in two worktrees, so two agents cannot silently be on the same one. And each tree has its own index, so git add, git stash and git checkout in one are invisible to the others. Everything they commit still lands in the same store, so branches and history stay whole.

3 · The rules that make it safe

1One issue, one branch, one PR

A builder that finds a second problem files it and keeps going on the first. This is what stops a change from growing until nobody can review it.

2The label is the lock

Claimed before the branch exists, cleared on merge, stale after a session. The town renders it, so you can see who holds what by walking the street.

3One tree per pen

Without worktree isolation the safe number of code-editing agents is exactly one — which is what runs today.

4A reviewer never files

Findings go to the owner, who ranks them. An agent that both finds and files is an agent marking its own homework.

5Explicit paths, never -A

git add names the files it means. This one is written from experience, twice.

6No agent merges its own work

Red before green, four suites, both games — and then a person decides.

Both hazards already happened here. git add -A swept fifteen of Rosa's scratch files into a commit that reached main. And Nacho could not write his own deliverable at all, because forbidding him the tree was the only way to stop him colliding with an in-flight edit. With a worktree, he simply writes. That is why these are rules and not advice.
